## Routing Level Awareness

This prompt supports four routing levels determined by the Entry Brief (`INPUT_ROOT/00-Entry-Brief.md`):

**Routing Levels:**
- **Skip** - Material is already complete or module doesn't apply. Do not generate.
- **Light Pass** - Back-fill/structure existing material. No live elicitation needed.
- **Constrained Run** - Full module, but downstream sub-outputs that touch pre-locked inputs defer to the locks rather than re-generate.
- **Full Run** - Module runs at full rigour as the framework specifies.

**Execution vs Delivery Mode:**
- **Execution mode** (internal): Include Upstream Anchors (verbatim quotes from Module 11), Traceability lines showing derivation, and strict translation discipline. This ensures quality control and proves derivation.
- **Delivery mode** (client-facing): Remove internal Upstream Anchors blocks, Traceability lines, derivation evidence and lifecycle controls. Preserve every substantive action, quantity, asset, response rule, threshold, owner, table and operating instruction. Delivery cleaning is not summarisation.

Never append internal controls, handoff envelopes, derivation traces or lifecycle ledgers to the client document.

**Routing Level Implementation:**
- **Skip:** Do not generate any output.
- **Light Pass:** Generate simplified output focusing on structure only. Skip detailed derivations and optional sub-sections.
- **Constrained Run:** Generate full output but respect pre-locked inputs without re-derivation. Mark constrained sections in output.
- **Full Run:** Complete every required section at full semantic depth in execution mode, then remove only the internal scaffolding for delivery. Do not collapse the result into an executive summary.

### Breakdown Guidelines

**Good Milestones:**

- Represent meaningful progress (not just "started" or "in progress")
- Have clear definition of done
- Take 1-2 weeks to complete
- Can be verified objectively

**Good Tasks:**

- Small enough to schedule honestly; use 2–8 hours only where it fits the actual work
- Have single owner
- Produce tangible output
- Connect clearly to milestone
- State the buyer response they support when the task is market-facing

**Common Mistakes:**

- Tasks too large ("Build the website") -- break further
- Tasks too small ("Open Figma") -- combine into meaningful work
- Milestones without definition of done -- add criteria
- No Claims Boundary checkpoint -- add review step
- Channel shorthand ("do LinkedIn") -- name the exact action, buyer, response sought, and next step
- Asset production without use ("write three posts") -- name where each asset enters the buyer-response sequence

## Vital Check

Module 12 has two thresholds. The Cycle Threshold checks whether the 90-day proof can happen and demonstrate what is intended. The Sustainability Threshold checks whether execution can continue beyond day 90. Assess both; each identifies different risks.

**Dependency Awareness:**

- [ ] Module dependency map reviewed — you know what must complete before what

**Work Breakdown:**

- [ ] Each 90-day proof action broken into week-level milestones

- [ ] Response Handling Map covers interest, questions, inbound requests, silence, and poor fit using the locked Module 07/09 route
- [ ] Asset Request List names what must be generated, where it is used, who owns it, and when it is needed
- [ ] In step-by-step founder guidance, the operating plan can be followed without opening or interpreting the upstream module files

- [ ] Specific, verifiable "done" criteria defined for each proof action

**Tracking Active:**

- [ ] Progress tracking system established in your PM tool
- [ ] First tasks entered and visible
- [ ] Tracking method matches one of the provided templates (or documented alternative)

**Capacity Realistic:**

- [ ] Resource allocation defined — hours per week per work type
- [ ] Allocation includes buffer (10–20%)
- [ ] Allocation is realistic given other commitments

**Claims Boundary Compliance:**

- [ ] Claims Boundary checkpoint built into milestone reviews (documented in tracking system or review template, not just in head)
- [ ] Conviction Links do not upgrade Must Qualify claims into unqualified outcome statements

**Conviction Trace (Test, Not Checkbox):**

- [ ] You can name the specific proof action it serves

## Common Mistakes

### Mistake 1: Over-Engineering the System

**Wrong:** Complex Gantt charts, dependency tracking software, resource leveling algorithms
**Right:** Simple list of milestones, basic tracking in existing tool, one-page view

The coordination system should take less than 5% of your execution time.

### Mistake 2: Forgetting Claims Boundaries

**Wrong:** Create tasks, execute tasks, realise output overclaims
**Right:** Include Claims Boundary checkpoint in every milestone review

### Mistake 3: No Buffer

**Wrong:** Allocate 100% of available time to planned work
**Right:** Keep 10-20% buffer for unexpected work and human reality

### Mistake 4: Skipping Reviews

**Wrong:** "Too busy executing to reflect"
**Right:** Reviews are how you catch drift before it compounds

### Mistake 5: Tasks Without Conviction Link

**Wrong:** Generic tasks that could belong to any business
**Right:** Every task traces to a proof action that traces to conviction

### Mistake 6: A Calendar With No Customer Path

**Wrong:** "Post Tuesday, email Thursday, review Friday"
**Right:** "Tuesday: publish the recognition post for [priority buyer] and invite replies to [question]. Thursday: send the proof piece to people who replied. Route qualified replies into [named conversation] within two working days."

A full calendar can still be commercially empty. Every market-facing task needs a buyer, a response, and a next step.

### Mistake 7: Making the Founder Decode Module References

**Wrong:** "Run 06B using S2, then use 07_04"
**Right:** "Generate the recognition post from the approved problem message. Publish it to [buyer group]. If someone replies, use the qualification questions in the sales guide."

Keep source references for traceability. Write the operator instruction in plain English.
