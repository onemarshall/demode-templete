# Module 12 Quality Gates

## Selected-cycle and entry interpretation — required

Apply current FW_15, FW_24 and Shared Contracts before the detailed instructions below. Preserve stable numbered read keys and legacy technical enum values such as `controlled-90-day`; the enum is a permission class, not a duration mandate. Render headings, dates, quantities and review events for the exact selected cycle. Retained 90-day calendars and three-action scaffolds are illustrative shapes only; adapt their repeated rows to every adopted action and actual selected period, never truncate accepted work or invent actions to fill the sample. Action count follows the accepted Direction, capacity, economic basis and decision thresholds. Required cycle-close review remains mandatory at the selected endpoint, with earlier binding review/stop conditions preserved.

A failed required entry emits only the shared dependency notice. A pre-lock or Wait preview exists only at its exact expressly permitted diagnostic scope with all other conditions satisfied; it cannot create normal strategy/coordination, a lock or a handoff. Source lock, client adoption, execution and release are separate. An override never waives Shared Contracts non-overridable boundaries.


## Strategy-to-action starter plans

Apply `FW_41`. Bring the current Starter Plan references and M11's exact accepted selections, adoption events and dispositions into the existing Working Cycle 01. This remains the single integrated first operating plan; it creates no second plan authority. Use `12_01` for shared assets, `12_03` for cross-functional sequence/dependency conditions, `12_05` for evidence, `12_06` for return conditions and `12_08` for transition. Preserve M11 commitments and all applicable response, rhythm, checklist and measurement sections. Block work that is unadopted, withheld, unresolved, stale, caught in circular dependencies or in conflict with capacity. Do not invent resources or approval to unblock it. Use the selected cycle for immediate and 30/60/90-day views. For later phases, inherit Direction’s selected horizon conditionally with decreasing detail. Adapt horizons under FW_24; do not create precise later dates, activity counts or budgets.

Before completion, check current source hashes, coverage of every required output, all dispositions, exact human adoption, inherited commitments and whether conflicts have been resolved. Static checks do not establish approval or a full semantic module pass.

## Planning-horizon and transition gate

Pass only when Working Cycle 01 preserves M11's selected duration and review event, distinguishes operating rhythm from commercial direction, and ends with evidence → review → decision → next controlled cycle. The transition must classify the affected decision as confirmed, strengthened, qualified, adapted downstream, returned upstream or stopped. Fail automatic cycle repetition or an unsupported return to upstream strategy.

> **Client-language translation gate:** Apply `FW_27` before passing any client-facing output. Preserve inherited commitments but translate framework labels into plain operating language; fail if a capable client cannot state what happens next, who owns it, how to respond and when to return.

## FW_32 Measurement and Review gate

Pass only when every scheduled evidence or implementation item inherits its action, decision, contract, consequence, driver and indicator IDs; exact M11 quantity, ownership commitment, route, proof action and threshold; baseline/evidence task; approval states; completion evidence; and return trigger.

Fail invented measures, costs or strategy; conflated events; missing or incomparable data treated as zero; observation presented as interpretation; or a strategy verdict made before data definition, implementation fidelity, evidence sufficiency, external factors, progression layer and local correction have been checked.

## Editorial Readability Gate

Apply `FW_27`. Pass only when the current objective, week's action, owner, response rule, quantity and threshold can be found on a first scan; weekly instructions do not restate the whole strategy; and source references explain an action or return path. Record structural evidence; keep cold-reader comprehension `pending`.

The plan must work without reopening the full pack. Preserve Commercial Cycle 01 as the cycle decision and keep Friday questions practical. Capture exact market language and route decisions separately from interpretation. Reject coordination detail that exceeds the scope of the controlled test.

### 12. Conviction Trace Test (Not a Checkbox)

**What "pass" looks like:**
For any randomly selected milestone, you can state aloud, in your own words, the actual belief it proves. Pointing to the label "Core Belief" is not enough.

If the coordination output will be reused as a public exemplar, the actual belief appears near the top of the output before the proof-action breakdown begins. A reader should not have to infer it from labels.

A trace that lives only in a checkbox is theatre. The test below is the real check.

**How to verify:**

```text
THE TEST: Pick 3 milestones at random. Run each one.

Milestone: _______________________

Step 1 — State the proof action it serves:
    "This milestone proves Proof Action [N], which is to ____________."

Step 2 — State the belief that proof action demonstrates:
    "If we complete this proof action, we demonstrate that ____________
    is true about the world / our market / our customers."

Step 3 — State the inverse:
    "If this milestone gets completed in a way that violates that belief,
    here's specifically what would go wrong: ____________."

PASS criteria for each milestone:

[ ] The output states the actual belief being proven before the first proof-action breakdown
[ ] Step 1 names a specific proof action, not 'general progress'
[ ] Step 2 names a belief in clear terms — not jargon, not framework
    terminology, not 'our Core Belief'. The actual content of the belief.
[ ] Step 2 respects Claims Boundaries. If the belief is still thesis-level,
    the trace does not speak as if it is proven fact.
[ ] Step 3 names a real failure mode — what miscalibrated execution
    would look like for this specific milestone. If you can't name what
    'doing it wrong' looks like, the trace is theatre.

All 3 milestones pass all 3 steps: PASS
Any milestone fails any step: Fix the derivation, not the checkbox

DIAGNOSTIC:

- Fails Step 1: The milestone is orphan work. Either tie it to a proof
  action or remove it.
- Fails Step 2: You're tracing to a label, not a belief. Go back to
  Module 01 / Module 05 and state the belief in your own words.
- Fails Step 3: You don't yet know what proving this looks like — which
  means you also won't notice when execution drifts off it. This is the
  failure mode the Entertainer illustrates. Stop and resolve before
  beginning the cycle.
```

**Why this is a test, not a trace:** The builder must explain the belief at stake each week, not simply point to a strategy document. In the Entertainer example, employees could point to the strategy deck, but no test caught execution drifting from the belief. This check tests understanding of that connection.
